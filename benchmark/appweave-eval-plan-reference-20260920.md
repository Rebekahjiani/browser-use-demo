## 0. 这个 Benchmark 的意义

这是一个**基准评测（benchmark）工作，本质是给 appweave 建一把可信、可复算的尺子**。意义有三：

1. **用"物理真相"定义"全和对"，替代主观感觉**。

评判标准一路锚定到 webarena-verified 的真实数据库表：网站的实体（商品/订单/用户…）与属性在 DB 里物理存在。

据此构建**期望 contextmodel** 作为标准答案，从此"全不全、对不对"有了客观分母。

2. **评的是"能力"，不是单次任务成功率**。

正如调研强调的：agent 完成某任务 ≠ 把网站探索全了。本 benchmark 评两样核心能力——

① 探索策略的**覆盖能力**（发现多少页面类型/状态/实体）；

② **构建 contextmodel 的还原能力**（harness+基模 能不能把 trace 里的网站语义完整、准确地建成 contextmodel——全不全、对不对）。

3. **它是可复用的"对照实验装置"，不是一锤子买卖**。

建成后，任何新探索算法 / 新 harness / 新基模，都能丢进**同一套评测流程、同一份标准答案、同一把尺子**打分。

让"优化"从拍脑袋变成**可回归、可对比的工程闭环**。

一句话：把"appweave 把网站理解得全不全、对不对"变成**可量化、可追溯、可迭代**。

### 这个 benchmark 跟已有的有什么不同（为什么有意义）

调研发现：**纯粹的"web 探索覆盖度 benchmark"已经存在**——软件工程领域的 WebExplor / WebRLED / VETL（评"发现多少 unique 状态/动作、代码覆盖率"，有 SOTA 演进），以及 Parallel WebBench（arXiv 2606.20724，评 web 探索的 trace 级正确性）。所以如果我们只评"谁覆盖得多"，那是重复造轮子。

本 benchmark 的独特价值，从第一性原理推：一个网站的"全部信息"物理上存放在**数据库**里，页面只是 DB 数据的投影（还投不全——很多字段不渲染、很多状态要交互才出现）。因此：

- **现有 benchmark** 的分母是"页面/代码/动作"——评的是**探索动作覆盖得多不多**；
- **本 benchmark** 的分母是"**真实数据库里的业务实体/属性**"——评的是**探索最终有没有把网站的业务语义挖全、挖对**。

一句话定位：**别人评"探索动作覆盖度"，我们评"探索的业务语义还原度"（用 DB 物理真相做分母）**。这一步把"覆盖"从动作层面提到理解层面，且分母是物理真相而非人工估计——这是没人做的，也是它站得住的根据。相关 benchmark 详见 `explore-algorithms.md` §6。

### 术语约定

- **trace**：探索策略采下来的原始证据（页面、交互、接口、AXTree）。
- **构建 contextmodel**：拿着一份 trace，用某个 harness（阿工/claudecode/codex）+ 某个基模（glm/deepseek/qwen），跑出一份 contextmodel 的整个过程。这是被评估的核心动作，两个 benchmark 都在反复做它。
- **期望 contextmodel / 标准答案**：从真实数据库表人工构建出的"这个网站就该有的实体+属性+关系全集"，是所有 contextmodel 的打分依据。
- **两个 benchmark**：本工作包含两个独立评测——Benchmark A 选**探索算法**（drive/browser-use/playwright 系谁采的 trace 好）；Benchmark B 选**构建组合**（哪个 harness+基模 构建的 contextmodel 好）。
- **确定性构建**：context-model 服务内部那段**纯代码、不含任何模型**的固定加工（`/ingest` 把 raw trace 整理成 EvidenceCatalog；`build` 经 buildPlatformCore → buildBusinessCore → normalize 拼出骨架）。它是 Benchmark B 的**参赛构建方法之一**，与各 AI 组合公平对比：跑同样的 trace、拿同样的打分。
- **评测方式**：所有被测对象**公平对比**——同一份标准答案、同一把尺子、同样的预算口径，按分数排名选最好的。
- **两个 benchmark 各评什么（维度划分）**：

    - **Benchmark A 评 trace 层的"全不全 + 真不真"**——全不全=探索发现的独立状态/页面/实体占标准答案的比例；真不真=trace 记录的是不是真实发生过的页面/响应（有没有编造、张冠李戴）。这评的是**探索策略的覆盖能力与忠实度**。
    - **Benchmark B 评 contextmodel 层的"对不对"**——提取组合把 trace 翻成业务语义模型时的**准确度/误报率**（模型会不会幻觉、编造 DB 里不存在的实体）。
    - 为什么这样分：trace 本身没有"对不对"，只有"全不全+真不真"（好的探索器录的是真实浏览器行为，不会假）；**"对不对"真正出问题在下一步——从 trace 提取 contextmodel 时模型会幻觉**。把"对不对"主要放 B、A 只看"全不全+真不真"，两个 benchmark 各评各的、归因最干净。

## 1. 核心评估流程

```
webarena-verified 网站数据库（物理真相）
   ↓ 人工+工具构建，冻结为标准答案
期望 contextmodel（实体/属性/关系全集）
   ↑ 比对打分（entity/attribute/关系 覆盖率 + 误报率）
实际 contextmodel（由 trace 经 harness+基模 提取）
   ↑
trace 采集（各自动探索策略）
```

**两层评估：**

- **Benchmark A（选探索算法）**：所有策略采的 trace，都用**同一个固定的 harness+基模** 来构建 contextmodel，再比谁构建出的更全更对 → 选出最好的探索算法。

（构建方法固定成常量，分数差异才能归因到"探索策略"本身。）

- **Benchmark B（选 harness+基模）**：固定用 A 选出的**同一份最好的 trace**，换不同 harness+基模 来构建 contextmodel，比谁构建得更好 → 选出最好的提取组合。

（trace 固定成常量，分数差异才能归因到"构建方法"本身。）

> 关键控制变量：评 A 时**所有 trace 用同一个 harness+基模 构建**；评 B 时**所有组合用同一份 trace**。
"构建 contextmodel"这个动作在两个 benchmark 里都在做——A 里它被固定，B 里它才是被测的变量。

## 2. 被测对象清单

### Benchmark A · 自动探索策略（被测对象，已按相关工作补全并核实）

被测对象覆盖"全站状态/页面覆盖自动探索"的**四大本质不同的范式**，每个都锚定确切的相关工作（论文/仓库，已核实 arXiv 编号）。详细调研见 `explore-algorithms.md`。

| # | 被测对象 | 范式 | 核心机制 | 相关工作锚点（已核实） | 状态 |
| --- | --- | --- | --- | --- | --- |
| **A1** | tracer-webapp `drive`（nodejs 启发式，无 LLM） | 启发式状态图爬虫 | BFS 同源遍历 + URL/DOM·AXTree 摘要状态判等 + epsilon-greedy 动作选择 + 约束满足表单填充（只填不提交）+ checkpoint 续跑 | **Crawljax**（Mesbah et al., ACM TWEB 2012；`github.com/crawljax/crawljax`） | 项目已有 |
| **A2** | **browser-use**（LLM 自主探索） | LLM 单任务循环（无显式 frontier） | LLM 全程决策；CDP 直连 DOMSnapshot+AX 混合观测；靠模型上下文循环 | **WebVoyager**（arXiv 2401.13919）/ **SeeAct**（arXiv 2401.01614）/ **AgentOccam**（arXiv 2410.13825） | 沙箱已搭好 |
| **A3** | **playwright-mcp**（MCP 驱动探索） | LLM + AX 树观测 | LLM 经 MCP 调 Playwright；观测=accessibility snapshot（无视觉）；逐快照决策 | **WebArena**（arXiv 2307.13854，a11y-tree 观测） | 待接入 |
| **A4**（新增） | **Go-Browse 式图搜索探索** | LLM + 显式状态图 | 把探索建成**图搜索**，跨 episode 复用探索信息，显式管理 frontier | **Go-Browse**（Gandhi & Neubig, arXiv 2506.03533） | 需复现/借鉴 |
| **A5**（新增） | **WebChallenger 式遍历建图** | LLM + 站点地图记忆 | **遍历每站一次，构建可复用"页面地图+元素行为"**，后续任务直接查图 | **WebChallenger**（Hwang et al.；`github.com/jayoohwang1/webchallenger`） | 需复现/借鉴 |
| **A6**（可选） | **WebPilot 式 MCTS 探索** | 搜索式 | 多 agent + 改进 MCTS（全局规划+局部 MCTS） | **WebPilot**（arXiv 2408.15978） | 视预算 |

> **复现算法还是用开源代码（第一性原理决策）**：测的是**算法（探索决策逻辑）**，不是某个 repo 的工程实现质量。据此：
>
> - **A2 browser-use、A3 playwright-mcp → 直接用官方开源代码**：它们本身就是被测的算法，没有"更权威的实现"，用官方代码保证评的是真身。
> - **A4 Go-Browse、A5 WebChallenger、A6 WebPilot → 优先用官方开源代码；代码不可用或无法适配成"全站探索器"时才按论文复现**：直接用官方代码=评作者实现的真算法、避免我们引入复现偏差。但它们的代码多为"采训练数据/单任务"写的，可能需包一层（给定入口URL+预算，跑其探索循环、收 trace）。**复现时只复现"探索决策逻辑"**（图搜索 frontier / 遍历建图 / MCTS），**观测/执行层复用我们自己的实现**，保证各策略在观测执行层面同质可比。
> - **核心原则**：能不动算法本体就不动（用官方代码）；必须改造时只动外壳（输入输出适配），不动决策核心；万不得已才复现，且复现范围严格限定在"探索决策逻辑"。
>
> **为什么补 A4/A5**：A1–A3 是你举的三个例子，机制本质不同（纯启发式 / LLM 循环 / LLM+AX 观测），但**没有一个是"以全站覆盖为显式目标"的**。A4（图搜索）和 A5（遍历建站点地图）是学界专门做"覆盖全站"的范式，直接回答"怎么探索才覆盖得全"，强烈建议纳入。A6 搜索式视预算可选。
>
> **A1 启发式算法说明**：`drive` 纯算法机制——normalized URL + DOM/AXTree 摘要状态判等；BFS 同源队列 + checkpoint 续跑做 frontier 管理；epsilon-greedy 动作选择；约束满足表单填充（默认只填不提交）；破坏性控件降级、跨域围栏、脱敏等护栏。它代表"纯启发式能采到什么程度"，与 LLM 系公平对比谁更全更对、成本谁更划算。
>
> **按调研纪律剔除的**（核不到确切出处，不写进被测清单）：LASER、AutoWeb/coverage-RL（arXiv 查无此名）；buttonmash（drive 蓝本，公开出处未核到，仅作内部参考）。playwright-cli+SKILL 与 A3 同属 LLM 驱动、机制同质，不单列。

### Benchmark A · 评估方法依据的相关工作

评"页面/状态覆盖度、全不全对不对"的口径，**不自己造**，逐条锚定相关工作。并按"两个 benchmark 各评什么"标清归属（A=评探索策略的 trace，B=评提取组合的 contextmodel）：

| 维度 | 定义口径 | 归属 | 依据的相关工作 |
| --- | --- | --- | --- |
| **状态判等** | 两个页面算不算"同一状态"：normalized URL + 结构摘要 | A | Crawljax 的 state abstraction（stripped DOM 判等） |
| **页面/状态覆盖度（全不全）** | 探索发现的独立状态数 ÷ 标准答案里的状态全集 | **A** | Crawljax 的 state coverage；WebArena/webarena-verified 的站点状态集合 |
| **站点图还原度** | 探索建出的图 vs 期望站点图（节点/边命中） | **A** | Go-Browse graph search；WebChallenger 页面地图 |
| **trace 忠实度（真不真）** | trace 记录的页面/响应是否真实发生过，有无编造、张冠李戴 | **A** | Parallel WebBench 的 trace 级诊断（arXiv 2606.20724） |
| **实体覆盖度（全不全）** | contextmodel 实体 ∩（界面可推导的）DB 物理表 的命中率 | A/B 共用 | 本计划 Phase 0 期望 contextmodel 作分母 |
| **正确性（对不对）** | contextmodel 实体/属性与 DB 表的映射准确度、**误报率**（含模型幻觉编造） | **B 为主** | 实体↔表映射参照 semantic-catalog 的 link/validate |
| **停止条件可解释** | 记录总动作/模型调用/重复动作/连续无新状态步数 | A | 调研 §9.4；Crawljax 的 crawl 终止条件 |
| **可复现性** | 同策略多 seed 的覆盖度方差 | A/B 共用 | RL/agent 评测通用做法（多 seed 报均值方差） |

> **A 看"全不全 + 真不真"，B 看"对不对"**（见术语约定的维度划分）。"实体覆盖度/可复现性"两个 benchmark 都要用，故标 A/B 共用。
>
> 所有被测策略**同一份标准答案、同一把尺子、同样的预算口径**（入口 URL、最大步数/页面数对齐），按上述维度打分排名，选最好的。

| 0.5 | **搭比对器**：输入任意 contextmodel.json，对照标准答案算 entity/attribute/关系 覆盖率 + 误报率 | `eval/compare-cm.ts` 打分器 |
| 0.6 | **比对器自测**：用手工假 contextmodel 验证算数正确（不需真实 trace） | 自测记录 |

状态分三层不混：浏览器观察状态 / 页面类型 / 业务实体（调研 §9.1 强调不要过早合并）。

**Phase 0 验收**：标准答案已冻结；给定任意 contextmodel.json（哪怕手工编的）能算出经得起抽查的覆盖率/误报率。

## 4. 关键设计决策（请确认）

1. **真相源优先级**：真实网站 DB > 手工标注 > 确定性构建结果。期望 contextmodel 由 DB 构建 + 人工冻结。
2. **顺序**：Phase 0（标准答案+打分器）→ Benchmark A（选探索算法）→ Benchmark B（选 harness+基模）。
3. **控制变量**：评 A 时所有 trace 用同一个 harness+基模 构建、评 B 时所有组合用同一份 trace；不同时换两个变量，否则增益无法归因。
4. **公平对比**：所有被测对象用同一份标准答案、同一把尺子、同样的预算口径，按分数排名选最好的，不设对照组。
5. **本阶段只做选型，不做优化**：先把"哪个最好"测出来，优化留待后续。
6. **期望 contextmodel 只含"界面可推导"的 DB 实体/属性**（已确认）：排除界面上根本看不到的内部字段/软删除标记/纯关联键，否则任何探索策略分数都有天花板、尺子不公平。见 Phase 0.3a。
7. **维度划分：A 评"全不全 + 真不真"、B 评"对不对"**（已确认）：trace 层只看覆盖与忠实，"对不对"（模型幻觉/误报）主要放 B。见术语约定与评估维度表。
8. **复现 vs 开源代码（第一性原理）**：能直接用官方开源代码就用（评的是算法真身）；必须改造时只动外壳不动决策核心；万不得已才复现、且只复现"探索决策逻辑"，观测/执行层复用我们自己的实现保证同质可比。
